# Промт для Claude Code — интеграция СИЗ-контроля с платформой

> Скопируй текст ниже в Claude Code, запущенный в репозитории СИЗ-контроля.
> Перед началом он сам определит стек проекта и подстроится.

---

Ты работаешь в репозитории приложения «СИЗ-контроль». Его нужно
интегрировать с нашей платформой (оболочкой web-desktop): приложение будет
открываться в окне-`iframe` внутри оболочки и доверять единому входу через
Keycloak. Сейчас у приложения свой логин по логину/паролю — его надо
заменить на вход через токен платформы, не сломав приложение на время
перехода.

**Сначала** изучи репозиторий и определи: язык и фреймворк фронтенда,
язык и фреймворк бэкенда, как сейчас устроены аутентификация и таблица
пользователей, где находится слой HTTP (middleware/фильтры) и где
выставляются HTTP-заголовки ответов. Кратко выпиши это перед тем, как
вносить изменения, и далее адаптируй шаги под реальный стек — не привязывайся
к конкретному фреймворку.

## Контракт с платформой (фиксированный)

- Пользователь приходит из Keycloak. Платформа передаёт его JWT внутрь
  `iframe` сообщением `postMessage`:
  ```
  { type: 'platform-auth', token: '<JWT>' }
  ```
  Сообщение приходит с origin оболочки (вынеси его в конфиг,
  напр. `PLATFORM_ORIGIN=https://platform.ru`).
- В токене есть claims: `sub` (постоянный id пользователя — главный ключ),
  `email`, `name`, и роли в `realm_access.roles` (массив строк).
- Проверять подпись токена нужно по публичным ключам Keycloak (JWKS):
  `${KEYCLOAK_URL}/realms/${REALM}/protocol/openid-connect/certs`.
  Issuer: `${KEYCLOAK_URL}/realms/${REALM}`.

## Что нужно сделать

### 1. Бэкенд: проверка токена и определение пользователя
- Добавь middleware/фильтр, который на каждый запрос к API:
  читает `Authorization: Bearer <JWT>`, проверяет подпись по JWKS, issuer и
  срок действия, и кладёт в контекст запроса `current_user` с полями
  `keycloak_id` (= `sub`), `email`, `roles`.
- Используй существующую библиотеку для JWT/JWKS под наш стек (не пиши
  криптографию вручную). Ключи JWKS кэшируй.
- Невалидный/просроченный токен → `401`.

### 2. База: связь со своим пользователем
- Добавь в таблицу пользователей колонку `keycloak_id` (строка, уникальная,
  nullable) и индекс по ней.
- Логику определения текущего пользователя сделай так: ищем по
  `keycloak_id`; если не нашли, но есть запись с таким же `email` — привязываем
  (записываем `sub` в `keycloak_id`) и дальше используем `keycloak_id`.
  Это разовая «миграция на лету» со старых аккаунтов.
- Подготовь миграцию схемы стандартным для проекта инструментом.

### 3. Авторизация по ролям (server-side RBAC)
- Защити операции проверкой ролей из токена (напр. изменять справочники
  может только `admin`; рядовой пользователь — только свои действия).
  Перечисли затронутые эндпоинты и проставь проверки.
- Никогда не доверяй роли/идентификатору, пришедшим с фронтенда — только
  тому, что в проверенном токене.

### 4. Фронтенд: получение токена от платформы
- Добавь слушатель `window.addEventListener('message', ...)`, который
  принимает только сообщения с `event.origin === PLATFORM_ORIGIN` и типом
  `platform-auth`, сохраняет `token` и подставляет его в заголовок
  `Authorization: Bearer` ко всем запросам к API.
- Если токена ещё нет (приложение открыли напрямую, не из оболочки) —
  оставь рабочим существующий вход как запасной, за фиче-флагом
  `PLATFORM_SSO` (см. п.6), чтобы ничего не сломать на время перехода.
- Прибери собственный экран логина из основного потока, когда `PLATFORM_SSO`
  включён (но не удаляй код целиком, спрячь за флагом).

### 5. Разрешить открытие в iframe оболочки
- На отдачу HTML приложения выставь заголовок:
  ```
  Content-Security-Policy: frame-ancestors 'self' https://platform.ru https://*.platform.ru
  ```
  Конкретные домены вынеси в конфиг.
- Убедись, что НЕ выставляется `X-Frame-Options: DENY` (иначе iframe
  заблокируется). Если он где-то проставляется — убери его.

### 6. Конфиг и флаги
- Вынеси в переменные окружения: `KEYCLOAK_URL`, `KEYCLOAK_REALM`,
  `PLATFORM_ORIGIN`, список доменов для `frame-ancestors`, и фиче-флаг
  `PLATFORM_SSO` (true/false).
- Обнови `.env.example`/README приложения.

## Критерии готовности
- Открытие приложения в окне оболочки логинит пользователя автоматически,
  без отдельного ввода логина/пароля.
- Запрос с валидным токеном проходит; без токена/с протухшим — `401`.
- Старый пользователь по совпадению `email` один раз привязывается к
  `keycloak_id` и дальше узнаётся по нему.
- Операции под ролями недоступны без нужной роли (проверено на бэкенде).
- Приложение открывается во фрейме с домена платформы и не блокируется.
- При `PLATFORM_SSO=false` приложение работает по-старому.

## Ограничения
- Не ломай существующую функциональность; изменения вне темы входа/прав не
  трогай. Минимально-инвазивные правки, по стилю и инструментам проекта.
- Не храни и не логируй токены.
- В конце дай короткий список изменённых файлов и что в них сделано, и
  отдельно — команды для применения миграции БД.
